Real example

❌ Without configuration

import { test, expect } from '@playwright/test';

test('get users', async ({ request }) => {
  const response = await request.get(
    'https://jsonplaceholder.typicode.com/users'
  );
  expect(response.status()).toBe(200);
  const data = await response.json();
  expect(data.length).toBeGreaterThan(0);
});

✅ With configuration

import { test, expect } from '@playwright/test';

test.describe('Users API', () => {
  test('[API] Should return list of users',
    async ({ request }) => {
    // Arrange
    const endpoint = '/users';

    // Act
    const response = await request.get(endpoint);
    const body = await response.json();

    // Assert
    expect(response.status(),
      'Status should be 200').toBe(200);
    expect(Array.isArray(body),
      'Response should be an array')
      .toBeTruthy();
  });
});

Step 1 — copilot-instructions.md

Global rules for the entire project

What is it?

A Markdown file at .github/copilot-instructions.md that defines project conventions.

Copilot reads it automatically on every interaction.


📁 .github/
  📄 copilot-instructions.md ← CREATE THIS

Content

# Copilot Instructions



## Project

API test automation framework using Playwright + TypeScript.

## Rules

- Use strict TypeScript, never `any`
- Tests follow the AAA pattern (Arrange-Act-Assert) with comments
- Every `expect()` must include a custom error message as the
  second argument of expect: `expect(value, 'message').toBe(expected)`
  — never as a second argument of the matcher
- Use `const` by default, `let` only when reassignment is needed
- No `console.log()` in tests
- Use `import type` for type-only imports

Step 2 — Scoped Instructions

Rules that only apply to files matching a pattern

What is it?

.instructions.md files that activate only for certain files.

The applyTo frontmatter defines a glob — Copilot only reads these rules when editing matching files.


📁 .github/
  📄 copilot-instructions.md
  📁 instructions/
    📄 spec-files.instructions.md ← CREATE

Content

---
applyTo: "tests/**/*.spec.ts"
---
# Spec Files

## Spec file structure
- Each spec file has a `test.describe` wrapping all tests,
  named after the endpoint
- Test labels: '[API] Should {expected behavior}'
- Tests use the AAA pattern with comments
- No complex logic in spec files
- Group related tests in the same describe block

## Naming
- Files: `{feature}.spec.ts` (kebab-case)
- Describes: name of the resource or endpoint
- Tests: start with "Should" + expected behavior

  • Does it have labels [API] Should ...?
  • Does it group tests with test.describe?
  • Is the file named posts.spec.ts?

Skill content

---
name: generate-api-tests
description: Generates complete test suites for JSONPlaceholder REST endpoints
---
# Generate API Tests

## Procedure
1. Identify the endpoint and HTTP method
2. Create the file `tests/{resource}.spec.ts`
3. Add a `test.describe` block named after the endpoint
4. Generate tests for:
   - Happy path (status 200, correct structure)
   - Resource not found (404 when applicable)
   - Response field validation
5. Each test follows the AAA pattern with comments
6. Every `expect()` includes a custom error message
7. Labels: `[API] Should {behavior}`
8. Run the tests with `npx playwright test {file}`

Step 4 — Agents & Sub-agents

From a simple agent to a system that generates, reviews, and runs tests

What is an Agent?

Skill

A step-by-step procedure

"Follow these steps to generate tests"

No tool restrictions or defined role

Agent

A role with boundaries

"You are a QA engineer with specific tools, restrictions, and your own judgment"

Decides how to solve, not just executes steps

Key: an agent has autonomy within defined limits. A skill is deterministic.

Why limit tools?

AgentToolsReason
test-generator read, edit, search Needs to read patterns and write files. Should not execute anything.
code-reviewer read, search Only analyzes. If it could edit, it would "fix" without supervision.
test-runner terminal, read Executes and reads output. Should not modify tests to make them pass.

If an agent has all tools, there's no separation of responsibilities. The output becomes unpredictable.

The Orchestrator

A coordinator agent delegates tasks to specialized sub-agents

QA Orchestrator
Coordinates the entire flow
→
test-generator
Generates tests
code-reviewer
Reviews code
test-runner
Runs tests

The orchestrator has agents: in its frontmatter — this gives it permission to delegate. Without it, it can't invoke sub-agents.

Feedback loop

The orchestrator isn't linear — it implements a correction cycle:

1. test-generator → generates tests
2. code-reviewer → analyzes → finds issues
3. test-generator → fixes (receives reviewer feedback)
4. code-reviewer → re-analyzes → OK
5. test-runner → executes → reports result

This is what differentiates an orchestrator from a sequential script: it makes decisions at runtime.

4a. Sub-agent: Test Generator

📁 .github/agents/
  📄 test-generator.agent.md ← CREATE 
---
name: test-generator
description: Generates test suites for REST endpoints
user-invocable: false
tools: ["read", "edit", "search"]
---
# Test Generator
## Role
You are a QA engineer that generates test suites.
## Instructions
1. Read files in tests/ to understand existing patterns
2. Load the generate-api-tests skill
3. Generate complete and executable tests

user-invocable: false → Only accessible as a sub-agent

user-invocable: false

---
# Code Reviewer
## Role
You review Playwright tests for quality and convention compliance.
## Checklist
- Does it follow the AAA pattern?
- Does every expect() have a custom message?
- Does it use baseURL from config (no hardcoded URLs)?
- Does it validate response structure?

Only read + search → cannot modify files

You run Playwright tests autonomously.

2. Analyze the terminal output
3. Report: passed, failed, and errors
4. If there are failures, suggest root cause

name: qa-orchestrator
description: Orchestrates test generation, review, and execution
tools: ["agent", "read", "search"]

# QA Orchestrator
## Flow
1. Use test-generator to create the tests
2. Use code-reviewer to review the code
3. If there are issues, use test-generator to fix them
4. Use test-runner to execute and validate
5. Report the final result

Invoke the orchestrator

  • Did the code-reviewer find anything to fix?
  • Did the test-runner execute the tests?
  • Did you get a consolidated final report?

Challenge: "Full Coverage Agent"

Put all layers to the test with a scenario that requires judgment


Request:

"We need a test suite for the endpoints /albums and /albums/:id/photos. It must cover: happy path, resource not found, structure validation, and the relationship between both resources (an album has N photos)."

Acceptance criteria

RequirementDetail
Functional coverage GET list, GET by id, GET 404, GET nested (photos of an album)
Contract validation Verify types of each field (id: number, title: string, url: string)
Resource relationship /albums/1/photos should return photos where albumId === 1
Team conventions AAA pattern, messages in expect, baseURL, descriptive names

The constraint

You can

  • Use all 4 layers you configured
  • Invoke agents and skills
  • Adjust your config files before starting

You cannot

  • Write test code by hand
  • Copy tests from another file
  • Give more than 1 prompt to the orchestrator

One single prompt. If your config is good, it should be enough.

Self-evaluation

CriterionPoints
Tests passed on the first attempt (no correction cycle from the agent) +2
Covers all 4 scenarios (list, byId, 404, nested) without intervention +2
Validates that /albums/1/photos returns photos with albumId === 1 +2
Generated code follows conventions from the first version +2
Achieved with 1 single prompt +2

Every point you lose is a gap in your configuration, not in the prompt.

Prompt Files

Reusable recipes that you invoke from the chat


Without prompt file

You write the same long prompt every time you want to generate tests

With prompt file

Save it once → invoke with / from the chat

Create a Prompt File

📁 .github/prompts/
  📄 generate-api-tests.prompt.md ← CREATE 
---
agent: agent
description: "Generates API tests for a REST endpoint"
---
Generate API tests for the endpoint: {{endpoint}}

Requirements:
- Use the skill generate-api-tests
- Include happy path, error 404, and structure validation
- Run the tests when done with npx playwright test

Invoke the Prompt File

In the Copilot chat, type / and select your prompt:

/ generate-api-tests
endpoint: GET /photos

  • {{endpoint}} becomes a field you fill when invoking
  • You can have multiple prompt files for different tasks
  • The prompt file inherits the project's instructions and skills

Prompt File ideas for QA

generate-api-tests.prompt.md
Generates a full test suite for an endpoint
review-test.prompt.md
Reviews a test file and suggests improvements
debug-failure.prompt.md
Analyzes a failed test and suggests a fix
generate-test-data.prompt.md
Generates test data for a schema

When the agent doesn't do what you expect

Debugging mental model for Copilot customization

Layer-by-layer diagnosis

If the output isn't what you expected, investigate bottom-up:

SymptomLikely causeFix
Ignores global conventions copilot-instructions.md not in .github/ Verify exact path
Applies rules to wrong files applyTo glob is wrong Test the glob against actual files
Skill doesn't activate Skill name doesn't match invocation Verify folder name vs how you reference it
Agent doesn't delegate to sub-agents Missing agents: [...] in frontmatter Add explicit sub-agent list
Agent modifies what it shouldn't Tools are too permissive Restrict to only necessary tools

Principle: explicit config > long prompts

Signs of bad config

  • You repeat instructions in every prompt
  • You need 3+ prompts for a correct result
  • Output varies a lot between runs
  • You copy the output and edit it manually

Signs of good config

  • A short prompt generates correct output
  • Anyone on the team gets similar results
  • Output is consistent between runs
  • You don't need to edit the generated code

Before vs. After

Without configuration With configuration
❌ Generic code ✅ Code aligned to your team
❌ Everyone gets something different ✅ Everyone gets the same standard
❌ Manual review of all code ✅ Automated review by sub-agent
❌ Manual test execution ✅ Autonomous execution by sub-agent
❌ Knowledge in one person's head ✅ Knowledge codified in skills and agents
